# Prompt log

This is an honest, chronological record of the prompts used to produce
this submission. All code, tests, README, registrar email, and this log
itself were generated by Claude (Anthropic's AI assistant) working from
these prompts — none of it should be represented as independently
human-written.

## Prompt 1

The user's opening request (paraphrased structure, full content
preserved in the session transcript) supplied five source files —
`applications.csv`, `banner.csv`, `transcripts.csv`, `emails.txt`, and
`mapping-spec.txt` — and asked for a complete take-home submission for
the "Campus Identity Collision" assessment (N2N Services / LightLeapAI),
to be built in a new `submission/` directory without modifying the
original files.

What it established:

**Policy precedence.** A three-level hierarchy: (1) the registrar's
(Priya Nandakumar) most recent written instructions in `emails.txt`
win any conflict; (2) nonconflicting provisions of `mapping-spec.txt`
(explicitly an unsigned draft that defers to the registrar) apply
otherwise; (3) IT's (Ken Ito) instructions apply only where they don't
conflict with the registrar. The prompt was explicit that IT's
"email is unique," "filename ID is authoritative," "SSN last four is
sufficient," and "skip internationals without SSN" positions are all
overridden by the registrar's follow-up email.

**Safety constraints.** Named directly in the prompt: email is never a
sole identity key; a filename-embedded Banner ID is evidence, not
authority, because scanner cover sheets can be reused; SSN last-4 is
never a sole identity key; conflicting or hard-to-defend evidence goes
to `HITL_REVIEW`; international applicants without SSNs are held, never
skipped or dropped; the program must never create a new Banner person,
write to a test/dummy record, or write to a deceased record; an
existing dual-enrollment person must be reused, not duplicated;
transfer credit must not be posted where Banner already shows posted
transfer credit; identity matching and credit posting are separate
decisions; and — because the supplied files contain no evaluated
course, equivalency, accepted-hour, or grade data — `write_credits`
must be `no` for every application, regardless of identity confidence.

**Expected implementation.** A dependency-free Python 3 CLI (standard
library only), invoked as `python -m src.main --data-dir challenge-data
--output decisions.csv`, structured as
`submission/{src,challenge-data,tests}` plus `decisions.csv`,
`prompts.md`, `registrar-email.md`, and `README.md`; explicitly no web
UI, database, API, or runtime LLM integration; `unittest` for tests
unless there's a compelling reason otherwise; `decisions.csv` with
exact columns `app_id,banner_id,bucket,confidence,reasons,write_credits,notes`
and specific allowed values and reason codes for each; strict rules
against any sensitive data (SSNs, full DOBs, raw emails) appearing in
notes, console output, exceptions, logs, or debug files; and a specific
required set of reason codes and normalization behaviors (name
punctuation/hyphens, `LAST, FIRST` vs `FIRST LAST`, middle initials,
unambiguous DOB formats, preferred names, East Asian name-order
differences).

**Initial acceptance criteria.** A 12-row expected outcome matrix
(app ID → proposed Banner ID → bucket) with expected totals of 5
`AUTO_MATCH`, 5 `HITL_REVIEW`, 2 `DO_NOT_WRITE`, 0 credit posts, plus
narrative interpretation notes for the harder rows (the Nguyen shared
email, the international hold, the Morales/Blake filename conflict, the
Brown employee birth-year conflict, the Patel OCR DOB conflict, the
Smith deceased record, the Student test record, the Kim
no-existing-person international case). The prompt asked that, if
inspection of the actual files gave a defensible reason to disagree
with any row, that disagreement be raised before changing the matrix.

**What was built in response.** After reading all five source files in
full, the resulting design matched the acceptance matrix on every row
using general, evidence-driven rules (no application ID is ever
referenced in the matching logic itself) — so no disagreement with the
matrix was raised. The implementation lives in `src/` (`models.py`,
`normalization.py`, `policy.py`, `matcher.py`, `main.py`), with 26
`unittest` tests in `tests/test_matcher.py` covering the 16 required
checks, all passing, and `decisions.csv` generated by running the
program (verified to match a committed copy byte-for-byte via a
dedicated test). `README.md`, `registrar-email.md`, and this file were
then written to close out the required deliverables.

One implementation bug was found and fixed during this same prompt's
work, before anything was reported as complete: an early version of the
matcher proposed the employee record `A00070001` as a `DO_NOT_WRITE`
candidate for `APP-92010` instead of correctly falling through to no
candidate / `HITL_REVIEW`, because the DOB-conflict branch didn't yet
check whether the filename candidate was a student record at all. This
was caught by comparing the first generated `decisions.csv` against the
acceptance matrix (not by a pre-written test), fixed by rejecting
non-student (`Employee`) filename candidates the same way a name
mismatch is rejected, and re-verified by regenerating `decisions.csv`
and re-running the full test suite (all 26 tests, including the
acceptance-matrix tests) to confirm the fix produced the expected 5/5/2
totals with no regressions elsewhere.
